# 扫描 R2 与向量识别并行

2026-09-29 增量实现已由 kd201 watcher 自动发布 Linux dev（`dab850f`，10:07 回读确认）；尚未部署 prod，真实 iOS/Android 批量识别与额度闭环仍待验收。基础请求、候选及确认入库契约沿用 [v1.1.0 扫描流程](../../v1.1.0/01-flows/scan-recognition.md)；本次只调整共享 API 的 I/O 顺序及相应计时，不改 Flutter 队列、SQL、配额锁、超时、重试、数据库结构或 Hyperdrive 配置。实际验证范围见 [本版本验证记录](../05-delivery/VERIFICATION.md)。

## 执行顺序

1. 验证 live session、请求幂等键、环境、图片/向量和服务端权益。
2. 使用既有 owner 级事务锁与条件写入领取本张图片的额度。超额、请求冲突、已完成重放在这里返回，不发起 R2 或向量调用。
3. 同时开始 R2 上传与向量识别；向量返回后可以继续目录补全，不需要等待图片上传。
4. R2 的拒绝立即转换为受控失败结果，防止另一路仍运行时出现未处理拒绝。两个分支结束后才决定审计及结算，不使用快速失败后遗留异步任务的方式，不把扣费或返还挪到响应之后。
5. 图片成功且识别结果已分类后，按原契约写审计、结算单张额度并返回。业务幂等键、响应字段、错误码和 HTTP 状态保持原约定。

图片上传失败时，向量调用可能已发生；这是并行的已知开销，不代表可以向用户收取成功识别额度。不会通过新增重试或延长请求 deadline 掩盖失败。

## 失败与额度规则

| 结果 | HTTP / 审计 | 额度及图片处理 |
|---|---|---|
| R2 成功，完整可用目录候选 | 200 / success | Free 消耗该请求的一次预占；Premium 不计入 Free 总额；保留图片 |
| R2 成功，未匹配 | 200 / no_match | 返还本张预占；保留失败分析所需的审计图片 |
| R2 成功，但目录候选不完整 | 200 / failed，沿用已有契约 | 返还本张预占，不因向量有候选就扣费；保留审计图片 |
| R2 成功，向量或目录访问技术失败 | 502 / failed | 返还本张预占；保留失败审计与图片 |
| R2 失败，不论另一分支成功或失败 | 500 / 不写 scan_record | 先等待另一分支结束，再尝试删除本请求图片并返还本张预占；R2 写入已完成但确认失败也纳入清理 |
| 审计 INSERT 失败 | 500 / 未创建审计 | 图片上传已经结束后才删除，避免“删除后迟到上传再次生成孤儿图片”；返还本张预占 |
| 图片清理失败 | 保持对应失败响应 | 沿用明确错误日志，继续尝试配额返还；不把清理失败标为成功，也不承诺外部 R2 与数据库原子提交 |
| 结算更新或回读失败 | 沿用错误响应，不伪造结算成功 | 已提交的结算由相同 request_id 重放恢复，不再次识别/扣费；数据库不可用、租约到期或进程终止仍沿用既有恢复边界，不在本次增加新事务或租约机制 |

## 多用户与 Gallery 批量隔离

Gallery 仍为每张图片一个 request_id / Idempotency-Key，不是整批一次扣费。Flutter 仍串行申请每张预占，后续识别允许交错完成。

- 同一个 owner 的多个 session 共享 Free 10 次额度；不同 owner 独立核算。
- 批量中每张成功/失败单独结算。一张失败只能返还其自身预占，不能减去其他图片已消耗的次数。
- 一张失败返还的额度可以被后续新请求使用；仍在运行的其他图片继续占用原预占，不会因此多放行。
- 活跃请求的并发重复调用仍冲突，已完成请求仍重放；成功重放不再扣一次，失败重放也不能重复增加可用次数。
- 返回额度仍来自既有服务端结算后回读；不改用批次开始时的本地预估来覆盖交错完成的结果。

本次新增测试使用仓库 PGlite 基座覆盖交错时序，并已将相同扫描路由测试切换到临时 PostgreSQL 18.6 容器验证：53 项通过，每个测试独立 schema、每个连接池实际取得 5 个不同 PostgreSQL backend PID；核心批量竞争用例另重复 3 轮通过。不新增或维护 D1/Miniflare 测试路径。该本地多连接结果仍不替代 Hyperdrive 查询缓存下的配额读新鲜度或真实双端 Gallery 验收。

## 观测计时变化

保留 scan_recognize_timing 既有日志字段与 >=1000 ms 阈值：

- image_ms：预占完成到图片上传完成。
- recognition_ms：向量分支实际开始到读取上游响应完成，不再减去 imageStored 时间。
- catalog_ms：向量返回到目录补全完成。
- audit_ms：图片与目录均完成之后到审计写入完成，不把等待另一并行分支的时间误算为审计耗时。
- total_ms、auth_ms、preflight_ms、settlement_ms 含义保持原边界。并行阶段重叠，不能把所有字段相加当作 total_ms，也不能把只记录慢请求的日志当成全量 P50/P95。

响应 elapsed 仍以秒表示，从向量分支开始到组装结果；现在包含两路汇合所需等待，而不再发生在图片上传之后。它不是客户端网络端到端耗时。

## 请求执行位置观测（2026-09-30，本地实现，未发布）

在共享请求中间件的既有 `api_request` 完成日志中增加三个字段，不另建请求关联，也不改响应、扫描业务逻辑或慢请求计时阈值：

| 字段 | 来源 | 含义与缺失规则 |
|---|---|---|
| `placement` | 请求头 `cf-placement` | 原样记录运行环境提供的放置标记；缺失为 `null`，不写死 `remote-IAD`，不解析或限制标记格式 |
| `ingress_colo` | `request.cf?.colo` | Cloudflare 入口节点；缺失为 `null`，不能当作 Worker 实际执行节点 |
| `country` | `request.cf?.country` | Cloudflare 提供的请求国家/地区代码；缺失为 `null`，不是用户国籍 |

沿用项目已有 Cloudflare Request 类型和可选链；Linux/Node 没有上述请求头与 CF 元数据时三个字段均为 `null`，不为 Linux 伪造地域。只选择这三个字段，不输出完整 `cf` 对象、城市、坐标或其他请求头；成功与错误响应都通过同一个完成日志出口。`null` 只表示未拿到标记，不证明请求没有远程放置。Cloudflare 仍将 `cf-placement` 视为可能移除的 beta 观测字段，不能依赖其格式实现业务路由或鉴权。

首轮 prod 发布并确认版本后，在 `toccards-api-prod → Observability → Events` 搜索 `api_request`，筛选 `POST /api/v1/scan/recognize`。从同一 invocation/trace 查看 `scan_recognize_timing`，结合 `audit_ms`、`catalog_ms`、`settlement_ms` 分析等待。沿用 `api_request.request_id` / `X-Request-ID` 的传输关联；扫描请求体的 `request_id` / Idempotency-Key 是另一业务契约，不混为同一标识。快请求以及未走到分段计时出口的失败可能没有 `scan_recognize_timing`，不能据此从统计中丢弃。

## Placement 两轮对照（待生产执行）

本轮保持 `[env.prod.placement]` 的 `mode = "smart"` 不变。直接同时发布扫描并行、新日志和定向 Placement 会混淆因果，不符合单变量对照：

1. **首轮：并行扫描 + 新日志 + 既有 Smart Placement。** 确认批准的业务源码、产物、生产版本及流量后发布并采集稳定基线。Hyperdrive 缓存策略保持不变；Linux dev 的验证不能替代生产地域基线。
2. **第二轮：仅替换 Placement。** 首轮样本与回退点确认后，保持相同 Worker 业务脚本及静态产物，只将下面的生产配置替换到原段落，并同步原有部署配置测试；不得同时保留 `mode = "smart"`：

   ```toml
   [env.prod.placement]
   region = "aws:us-east-1"
   ```

   这是待执行配置，不是本轮已经修改或发布的状态。发布前复核源数据库区域；历史 Hyperdrive 主机名给出 us-east-1 线索，不替代源数据库区域元数据确认。Placement 调整 Worker 执行位置，不迁移数据库、不换 App API 域名，也不要求实际节点必须名为 IAD。两轮之间不调整 Hyperdrive 缓存、连接上限、SQL、超时、重试或其他业务行为。若需调整，必须另开测量窗口。
3. **配置与回退核验。** 只读回读现网 Placement 区域、deployment/version/流量、Worker 脚本及绑定/缓存配置，确认请求属于本次版本；同时核验两个 prod Admin 入口，不能以 API 域名副本替代 Pages 入口。保留首轮 Smart Placement 的生产版本及配置快照；发生回归时按批准的回退流程恢复首轮状态，回读配置后单独划分回退时间窗。
4. **效果对照。** 同接口、地区、状态口径和采集方式比较完整请求样本，包含快请求及失败请求；按 invocation 去重，记录时间窗、版本、样本数及日志采样/缺失情况。分别报告成功、失败和总量，避免快速失败制造“延迟改善”；分别查看 AU 的 SYD/ADL 入口及其他国家，补验登录、Search、Portfolio。分段慢日志仅用于诊断；P50/P95、`duration_ms > 5000` 占比需使用全量 `api_request` 或同口径平台数据，不能混用计时来源，也不能把慢日志作为分母。客户端完整请求耗时需要真实客户端独立测量。

用户提供的历史基线为 AU 108 次、Worker P50 1.707 秒、P95 6.643 秒、超过 5 秒 45 次（41.7%）；本轮未取得原始全量样本、时间窗或对应版本，未独立复算，不能直接视作首轮发布后的控制组。目标可设为同口径 P95 <3 秒、超过 5 秒占比 <5%，这是待验收目标而非收益承诺。

主库附近执行可能减少多次串行跨区域数据库往返，但现有四百多毫秒分段并非地域根因的充分证据。若配置与请求放置证据已表明靠近主库，`audit_ms` 等仍高，应继续检查连接池等待、数据库执行及其他链路；不靠再次改变地域猜测修复。原有缓存一致性验收缺口不因增加日志或切换 Placement 自动关闭。

## Android 新账号扫描入口修复（2026-09-29，隔离测试包已验证）

Pixel_8 新 UID 100044 已取得服务端 Free 额度，但 Android 当前未配置本地订阅商店，本地权益保持 unknown，原 Scan 入口因此拒绝打开 Gallery。修复限定为：仅在 Android、本地订阅商店未配置、刷新本地权益仍 unknown 时，额外刷新一次服务端 quota；只有请求成功且结果是服务端权威状态才继续原有额度检查。失败、非权威初始值或陈旧缓存不放行，额度为 0 时仍执行原有等待/付费提示逻辑。

这不是将 unknown 强制改为 Free：全局 SubscriptionState、StoreKit、订阅缓存和服务端权益/扣费规则都不改。iOS 不进入新增分支，仍保留原有本地权益校验、失败阻断与同步流程。已有点击互斥覆盖刷新等待，防止快速重复点击打开多个选图器。修复已在隔离 Pixel_8 Android 测试包验证：UID 100044 的 A 组 8 张通过真实选图、端侧模型和 dev 识别，恰好消耗 8 次、剩余 2 次；上午 B 组因系统 LOW_MEMORY 回收而未提交；下午续测已选择 6 张，新增 2 次成功消费后总额度用完，但发生 Android 模型输出编码前台 OOM。重开后 0 次额度门禁正常，剩余 4 张 Waiting 与队列稳定性未完成，B 组整体验收不通过。随后同 APK 卸载重装、新 UID 100045 在相同 A/B 条件下重现该前台 OOM，重装没有修复；没有重置旧 UID 的服务器账本。iOS 对照及相关回归通过，但未做 iOS 真机或真实 StoreKit 验收。
