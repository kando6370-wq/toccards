# App 向后兼容开发规则（v1.1.2，阅读版）

更新日期：2026-10-14（Asia/Shanghai）。本版按用户确认的兼容原则约束后续开发，供产品、开发和评审人员阅读；开发时配套使用 [AI 执行版](../03-data-api/app-backward-compatibility-ai-guide.md)。

本版本的 App 兼容资料只维护本文与 AI 执行版两份。本文解释规则与例子；AI 执行版集中提供开发动作、已有测试的运行方式、覆盖缺口和必要证据摘要。规则制定不表示全部旧 App 已经通过兼容验收。

本文是后续开发规范。仅确认或落实规则时，只维护规则及文档入口；具体功能需求、已证实且属于当前任务的兼容 BUG，或明确的补测要求，才触发相应开发与验证。测试覆盖缺口本身不构成 BUG 或自动整改任务。

## 1. 我们要解决什么问题

**服务端升级、新 App 增加功能以后，旧 App 仍然可以用原来的接口，完成它原来就有的功能。**

> 以现有 `/api/v1` 对外约定为基础；新功能优先复用 V1，新增请求字段可选且省略时保持旧行为，新增响应字段须能被旧 App 忽略；无法兼容扩展时只为受影响功能新增 `/api/v2`，同时保留 V1。

这里的“旧接口不改”，指对旧 App 的约定保持兼容。服务端内部可以修 BUG、优化性能、调整查询或存储实现，但不能因此让旧请求失败、旧返回无法解析或原有业务失效。

旧 App 不需要获得新功能，也不需要为了继续使用原有功能而升级。App 的版本号与 API 版本分别管理，发布一个新版 App 不代表必须新增 V2。

## 2. 基础版本指什么

基础是现有 V1 的对外约定，包括接口路径、请求方式、请求字段、返回字段和原有业务行为。后续不能每发布一次，就把新 App 的要求变成所有旧 App 的要求。

本次沿用 [App 1.0.4+ 兼容契约](../../v1.1.1/03-data-api/app-compatibility-contract.md)的支持范围，不重新选择最低支持版本。仓库已有 1.0.4+161、1.0.5+163 两组固定旧源码供回归；它们是验证用的客户端基线，不等于 API 主版本，也不证明所有正式安装包已经实测。

“当前”是本次确认的接口基础，不能用后续改过的代码覆盖旧约定。如果发现当前实现本来就与旧 App 不兼容，应单独定位和修复，不能把错误行为登记成新的兼容标准。

## 3. 哪些改动可以继续使用 V1

| 后续改动 | 可以继续使用 V1 的条件 |
|---|---|
| 增加查询条件或业务参数 | 新字段可选，旧 App 不传时按原逻辑处理；不能让旧请求多出必填参数。 |
| 增加展示信息 | 保留全部原字段及其类型、含义；增加的返回字段能被旧 App 忽略，不影响解析。 |
| 修 BUG、提高速度、优化内部实现 | 恢复既定预期，或在保持对外行为的前提下优化。 |
| 给已有数据增加属性 | 旧 App 仍能读和执行原有操作；旧 App 编辑时不能清空它不知道的新属性。 |

新增返回字段与修改原字段是两件事。例如，增加一个独立的展示字段可以兼容；把 `card_ref` 从字符串改成数字，会影响旧 App 的解析。新增状态值也可能破坏旧 App，不能因为“只是新增”就直接认定兼容。

## 4. 哪些情况需要新增 V2

当新需求必须改变原接口的请求、返回或业务含义，且无法通过兼容扩展满足时，新增受影响的 V2 接口：

- 原接口必须新增旧 App 无法提供的必填参数。
- 必须删除或改名旧字段、改变字段类型、返回层级或分页结构。
- 必须采用旧 App 无法理解的新状态或不同的业务操作含义。

V2 只覆盖有实际需求的功能，不把整个 V1 复制或整体替换。旧 App 继续调用原 V1；新 App 只在需要新协议的功能上调用 V2，其余功能仍可使用 V1。V1 与 V2 继续遵守相同的账号归属、权限和购买权益要求。

如果需求只是新增一个独立功能，且不改变任何已有接口，可以在 V1 下新增独立接口；若需求明确指定 V2，则按已确认的设计执行。是否需要 V2，取决于是否改变旧约定，而不是功能是不是新的。

截至本次文档编写，仓库主要业务仍挂载在 `/api/v1`，本文没有创建 V2。实际需要时，再按具体需求实现。

## 5. 三个例子

以下是规则示例，不代表已经新增这些业务字段或接口。

**例一：增加收藏备注。** 原来的收藏信息照常返回，另外增加备注字段。旧 App 忽略备注，新 App 可以展示。旧 App 只修改名称时，服务端保留已有备注。这种情况可以扩展 V1。

**例二：增加可选筛选。** 新 App 查询时多传一个筛选参数；旧 App 不传时，仍得到原规则下的结果。不能因为增加筛选，就改变旧 App 的默认结果范围。这种情况可以扩展 V1。

**例三：更换返回结构。** 原来返回卡牌列表，新需求必须返回按新规则分组的另一种结构；如果直接替换，旧 App 无法解析。保留原 V1 列表接口，为新结构提供 V2。

## 6. 后续每个需求怎么开发

1. **确认影响。** 找出现有接口、旧 App 调用方式，以及本次会改变哪些字段和业务行为。
2. **选择方案。** 能兼容扩展就复用 V1；必须改变旧约定时提供局部 V2，并写清保留的 V1 行为。
3. **完成开发和文档修改。** 只修改当前需求涉及的代码，复用现有能力；没有已确认兼容问题时，不为“整改”批量改动旧接口。
4. **完成后再验证。** 只验证受影响的功能及其共享调用方，确认旧请求仍可用、旧返回可解析、业务结果正确。没有影响的功能不额外测试。
5. **如实交付。** 写清已通过、失败和未运行项。源码测试、真机测试与线上验收分别报告。

如果影响共享数据，还需验证“新版写入 → 旧版读取／原有编辑 → 新版再读取”。不能只看 HTTP 200 或是否崩溃，还要确认数据没有丢失、价格和额度没有算错、权限没有放宽。

涉及 Flutter 时保持 iOS 和 Android 的既有支持边界；单平台结果不能代替另一平台。旧包、设备或账号不可用时，明确记录待验，不能直接声称全部旧 App 兼容。

## 7. 本次文档整理的边界

本次交付阅读版与 AI 执行版，并在版本入口和根 AGENTS.md 中提供导航。测试说明和必要证据摘要已合入 AI 执行版，重复的独立说明与验证文档已删除。不会仅因为制定兼容规则，就要求重写所有旧接口、批量创建 V2、改造全部发布入口或建设完整数据库回退体系。数据库、缓存、部署及真机的专项验证按具体改动影响执行，既有未完成验收继续保留。

原计划 P01–P06 不再作为必须顺序实施的工作清单。已有兼容回归继续复用，兼容 CI 保持既有异步反馈约定；新增强制门禁、变更最低支持版本和发布流程，均需成为单独明确的需求。

当前没有已证实的兼容故障需要在本次文档任务中修改代码。后续发现具体问题时，按项目 BUG 规则处理；只有规则或文档改动时，完成后检查链接、引用和差异即可。
