# App 向后兼容整改开发计划（v1.1.2）

编写日期：2026-10-13（Asia/Shanghai）。方案依据为 `main@7db7d63bbc76a7eb3a9e5783d2d61907a305e7f7` 的代码、当前兼容文档及本次讨论；实施分支为 `codex/app-backward-compatibility`。

决策状态：开发方案，供后续分阶段实施与评审使用。本文不表示整改、发布检查或完整旧包兼容已经完成，也不构成 Git push、部署、远程数据库迁移、生产写入或外部购买调用的授权。基线提交用于定位编写依据，不要求后续开发停留在该提交。

## 1. 目标与范围

目标：每次新服务端或新 App 发布后，仍受支持的旧 App 能连接当前服务端，完成其原有业务，且请求、响应、错误语义、共享数据、身份隔离、扫描额度和购买权益保持正确。

- 延续 [App 1.0.4+ 服务端兼容契约](../../v1.1.1/03-data-api/app-compatibility-contract.md)与 [C01–C13 验收矩阵](../../v1.1.1/05-delivery/app-compatibility-acceptance.md)，不建立另一套相互冲突的支持口径。
- 支持范围从 App 1.0.4 起；按实际已分发、仍受支持的营销版本和存在协议差异的构建登记。源码标签不证明商店分发或正式安装包可用。
- 保持 iOS 16+、Android API 24+ 的既有平台边界；Android 正式包基线和 Premium 售卖范围需要产品／发布负责人确认，不能根据 iOS 结果外推。Web 扫描及 1.0.4 之前的 pHash 协议不纳入本次范围。
- 主要实施范围是后端合同、冻结旧客户端测试、PostgreSQL／缓存兼容、发布前检查和制品验收；Admin 与插件作为独立 API 消费者补充相应合同。
- 新功能不要求旧 App 获得；旧 App 原有资产和操作不得因新功能失效。不通过提高最低 App 版本、接受客户端自报权益或把错误改为空数据来消除兼容失败。
- 本次不预先创建 `/api/v2`，不整体重构业务层，不引入通用契约平台，不增加业务 schema。只有具体需求证明必要时才提出对应变更。

## 3. 开发必须保持的契约

| 边界 | 实施要求 |
|---|---|
| 请求与返回结构 | 保留旧路径、方法、字段名称、类型、可空性、分页和响应包络；新参数不能变成旧请求的必填项。可选字段新增也要由实际旧解析器验证。 |
| 业务语义 | `card_ref` 保持字符串；缺价 `null` 与合法零价 `0` 分开；币种、精度、时间范围、部分历史和排序保持既有定义。 |
| 错误与状态 | 保持原 401/403/404/409/422/5xx、业务码和 Content-Type 的含义；未知新枚举／状态不能未经验证直接流入旧包。 |
| 认证与权益 | 维持有效旧 session、Token Refresh 及 owner 隔离。兼容处理不能信任客户端自报 Premium、UID 或未验证交易，也不能通过重置现有会话或更换密钥规避问题。 |
| 幂等与额度 | 同业务重试保留幂等键；区分传输 request ID 与业务幂等键。Free 终身 10 次、完整 Matched 扣减、失败释放、Premium 不扣 Free 等规则沿用原契约。 |
| 新写旧读旧编辑 | 当前版本写入旧版支持的业务数据后，旧版能读取和原有编辑／删除；旧编辑不能误清空新版字段或破坏新版数据。新功能独有数据需明确视图／隔离策略，不隐藏旧资产。 |
| 协议演进 | App 营销版本与 API 主版本分别管理。仅在无法保持旧契约时提出 `/api/v2`，继续维护 `/api/v1`；只在受影响模块做适配并复用既有业务实现。 |
| 客户端能力信息 | 新增版本 Header／参数只能是可选项，缺省保持旧行为；不得作为授权证据。现有卡牌请求的 `response_version=2` 已被旧源码使用，不能当作“只有新 App 才发送”的开关。 |
| 数据与缓存 | PostgreSQL 迁移和缓存格式同时考虑新旧代码共存；只对发生格式／语义变化的缓存调整版本，不盲目清空业务数据。 |

契约结构、错误语义或业务规则确需改变时，应先提出增量设计与支持影响，再决定适配或新版本接口；不能通过更新预期值、弱化断言或修改冻结旧源码掩盖破坏。

## 4. 分阶段实施

按 P01 → P02 → P03 → P04 → P05 → P06 推进。每阶段形成可独立审查的提交；代码与对应契约说明同步更新。发生真实 BUG 时遵守根 AGENTS.md 的复现、失败证据、最小修复、回归和 Code Review 规则。

### P01：固定支持集合并增强报告

主要落点：[基线登记](../../../../scripts/app-compatibility-baselines.json)、[编排脚本](../../../../scripts/check-app-compatibility.mjs)、[脚本测试](../../../../scripts/check-app-compatibility.test.mjs)。

1. 保留现有两组不可变源码 SHA 和 tag 校验；为实际存在的平台／分发构建补充证据，缺失的制品信息明确待确认，不伪造 IPA/APK 哈希。
2. 在原报告上增加场景 ID、基线版本／构建、必需场景集合及通过／失败／未执行／不适用结果；不适用必须记录依据，不能把未执行计为成功。
3. 记录测试所用依赖锁文件、合同定义和迁移集合摘要；继续区分旧源码使用当前依赖运行与历史签名制品。源码报告保持 `git-source-contracts-only`，不升级成真机证明。
4. 保留本地 dirty 工作区运行回归的能力，并如实标记；发布候选默认要求干净 checkout，不能把 dirty 检测仅作为不影响放行的提示。
5. 约定发布后撤回或变更报告所依赖输入时必须重验；报告过期策略在接入前明确，不只检查文件存在或 `status=passed`。

验收：空／漂移基线、缺少必需场景、旧报告格式、不一致输入、缺失前置条件均产生明确失败；现有固定旧源码执行和反例测试继续有效。

### P02：补齐原有业务合同

主要落点：[API 合同](../../../../apps/workers-api/src/compatibility/app-contract.test.ts)、[旧端合同](../../../../apps/flutter-app/tool/compatibility/client_contract_test.dart)及对应模块已有测试。按业务体量拆分测试文件即可，不预先引入通用框架。

| 关联矩阵 | 必须补的场景 | 关键业务断言 |
|---|---|---|
| C01、C03 | 配置、目录、卡牌详情、行情、汇率；扩展有实际差异的游戏／价格维度 | 保留旧升级字段、字符串 ID、分页、零价／缺价；失败显式呈现，最低支持版本不意外提高。 |
| C02、C09 | 匿名／注册登录、找回密码、Refresh、登出、账号删除、切号、请求 ID | 发布前有效会话在候选服务端可用；刷新后的旧调用可继续；跨 owner/session 请求不越权，不确定重试不重复写。 |
| C04、C13 | Folder、Collection、Wishlist、偏好、重排／默认文件夹；新写→旧读／旧编辑→新读 | 资产完整、owner 隔离、幂等重放与冲突正确；旧端未提交的新增字段被保留。 |
| C05、C06 | reserve→recognize→Review→confirm；JPEG+512 维向量、可选参数、TCG/Sports 既有范围 | 完整成功扣一次；No Match／技术失败释放；并发、超时和迟到响应不双扣、不重复入库；Premium 不占 Free。 |
| C07 | Fresh Purchase、Restore、同步、到期／退款、不同 session、无有效 proof | 旧错误可解析；仅可信 Apple 证据与会话证明授予服务端权益；本地受控测试与真实 Sandbox 结果分列。 |
| C08、C09 | 卡图／分享、受保护扫描图、网络失败和重试 | URL、鉴权、内容类型保持语义；传输失败不变成成功，也不造成写请求重复执行。 |
| C12、C13 | Home/Card Detail Performance、估值历史、Free/Premium、部分历史和当前写入后旧读 | 金额／币种／历史正确；缺数据、合法零值和服务失败不混淆；未授权请求不泄露资产。 |

补测试时必须同时检查旧代码发出的请求、旧代码解析结果和服务端副作用。现有回放 adapter 按 JSON 解码请求流，并按路径简化鉴权断言；扩展扫描 multipart、认证刷新及权益请求时，应按实际 Content-Type、Header 和字段验证，不能直接套用现有 JSON-only 假设。

至少增加字段类型变化、零价被改成 null、错误被改为空列表、未知额度状态、重复消费／入库、跨 owner 读取和旧编辑清空新增数据等可重复失败反例。恢复正确实现后，同一测试必须通过。临时故障注入只在隔离测试环境执行。

Admin 和插件分别验证其请求形态、鉴权、错误与返回详情；插件继续使用独立 Key／限频，不接入 App session、订阅或扫描额度。插件外部客户端源码缺失时，冻结可获取请求样本并明确证据边界。

验收：两组固定旧源码完成本阶段适用场景；失败反例确实暴露业务破坏。没有真实网络／外部服务的测试只报告合同层结果，不关闭 C11 制品待验项。

### P03：验证完整 schema、运行入口与版本共存

对应 C10，并与 C04/C05/C06/C12/C13 的共享数据和并发场景联合验证。

主要落点：[PostgreSQL 实现与迁移](../../../../apps/workers-api/src/db/postgres)、[数据库适配](../../../../apps/workers-api/src/db/postgres-database.ts)、[Cloudflare 入口](../../../../apps/workers-api/src/index.ts)、[Linux 入口](../../../../apps/workers-api/src/linux/server.ts)及测试基座。

1. 保留 PGlite 快速合同；另建立隔离 PostgreSQL 18 验证路径，加载目标完整迁移集合，覆盖并发、约束与真实 HTTP 请求。不能在测试失败后静默退回部分迁移。
2. 分别验证空库初始化、已有目标前一 schema 升级、候选服务端读取升级后的数据。选定上一实际可回退的服务端 SHA，验证它也能处理新 schema 和候选版本已写入的数据。
3. 两版本混合调用同一幂等请求、扫描 reservation 和资产更新，确认账本与最终状态一致。HTTP 会话、multipart 和超时场景必须能执行真实请求，回放仅作为独立快速层。
4. 迁移采用先扩展、再迁移、最后清理：保留旧字段／旧读写能力，先验证数据回填与共存；直到旧消费路径及明确回退版本不再依赖时，才另行提出删除。双写仅在迁移确有需要时引入，并验证一致性。
5. 检查 [KV 缓存](../../../../apps/workers-api/src/data-source/kv-cache.ts)和 [Cache API](../../../../apps/workers-api/src/data-source/cache-api.ts)在新旧值、命名空间与过期期间的行为。
6. Linux Node 验证与 Cloudflare Workers 验证分开，特别覆盖 Service Binding、重定向、Header 和缓存差异；无法本地复现的环境差异列入获授权环境验证。

本阶段不要求为兼容测试新增业务 migration。后续真实 schema 需求只能进入 PostgreSQL 迁移目录，并先说明兼容、备份、回退和环境影响；远程执行需独立授权。D1、旧 D1 schema／测试基座／回退路径均不参与。

验收：候选服务端与选定上一版本在目标 schema 上的适用合同通过；不兼容时阻止滚动／回退方案放行。代码回退与数据恢复分别验证，备份成功或目录可读不能代替恢复演练。

### P04：把兼容结果接入全部发布入口

采用一个范围明确的发布检查入口，复用 P01 报告；可按需新增 `scripts/check-release-compatibility.mjs` 及其测试，文件名为实施建议，编写本计划时尚不存在。

发布检查需要形成下面的关联链：

```text
干净候选提交 + 固定旧客户端 + 合同/依赖/迁移输入
    → 同一 SHA 的兼容测试报告
    → 构建清单引用报告摘要，并记录批准产物摘要
    → 发布前验证来源、SHA、场景完整性及全部摘要
    → 在取得相应授权后上传/切流/执行环境变更
```

测试报告先绑定源码及测试输入；构建完成后由构建清单关联报告和实际产物。禁止校验完一份产物后重新构建另一份未经比对的产物用于发布。

| 发布入口 | 接入位置与要求 |
|---|---|
| prod Workers | [deploy:prod](../../../../apps/workers-api/package.json)：在首次远程发布写入前验证候选与产物；保留既有构建和环境隔离。 |
| 手工 Linux dev | [deploy-dev.mjs](../../../../deploy/linux/deploy-dev.mjs)：在 SSH 上传／远程执行前检查。dry-run 保持只在本地构建；dry-run 不等于已通过发布验收。 |
| Linux watcher | [watch-branch.sh](../../../../deploy/linux/ci/watch-branch.sh)：读取目标 SHA 对应的可信 CI 报告；pending／缺失时等待，不标记已部署，也不能推进状态导致后续永远跳过该 SHA。 |
| Linux CI 与服务器发布脚本 | [linux-test-deploy.yml](../../../../.github/workflows/linux-test-deploy.yml)、[deploy-release.sh](../../../../deploy/linux/ci/deploy-release.sh)：下载产物后重新验证清单关联；直接调用服务器脚本也不能绕过必要校验。 |

发布报告必须来自指定仓库／可信 workflow 的实际运行，不能接受任意可编辑 JSON 自报成功。保留兼容 workflow 的只读权限，不向旧客户端测试注入生产 Secret，也不要求在部署服务器安装 Flutter。

PR merge ref、PR head、合并后的 main/dev 和最终发布 SHA 可能不同；必须验证最终候选 SHA。开发分支 push 不触发当前兼容 workflow 时，可以按指定 ref 手工触发检查，并核对报告中的实际 SHA，不能复用相似分支的通过结果。

检查失败、取消、超时、缺报告、场景缺失、摘要／SHA 不符或不受信来源时，必须明确拒绝发布；不设置默认跳过开关。工具能约束接入的发布入口，无法宣称已禁止所有持有生产凭据的人手工运行 Wrangler；生产凭据／控制台权限收口如有需要另行提出授权方案。

Admin 发布继续同时验收 Pages `toccards-admin` 与 Workers assets 两个入口；若变更发布命令涉及 Pages 自动发布，需先核对并单独授权调整其实际配置。只发 Admin 的候选仍要验证它调用的生产 API 契约，不夹带未批准的后端增量。

验收：对上述入口进行隔离失败注入，确认失败发生在远程写入之前；pending 后同 SHA 的成功结果仍可恢复推进；正例只发布与报告关联的产物。推送／合并仍不依赖恢复分支 required check。

### P05：正式旧包、双端和外部服务验收

对应 C11，按各平台适用的 C01–C13 场景执行制品验收。

1. 由产品／发布负责人确认受支持分发集合，取得 iOS 最早支持版本、上一已发布营销版本及协议差异构建；Android 先核对真实分发事实、签名包及版本。
2. 登记 Bundle／包名、平台、营销版本、构建号、源码 SHA（可确认时）、制品 SHA-256、API origin、系统版本、设备、测试账号和数据种子。
3. 固定旧源码生成的 dev 包在 Linux 独立环境预验；正式签名包按其实际可达 origin 验证。正式包不能连接候选服务端时，明确预发布证据缺口及发布后补验安排，不把改配置重编包等同于历史安装包。
4. 执行 P02 原有关键路径及新版写→旧包读／编辑→新版再读；购买／恢复／退款等生命周期需要获授权的 Apple Sandbox／TestFlight 和实际设备证据。
5. 正式包缺失、权限不足或外部服务不可用时，逐项记录原因、影响、责任人和补验条件；适用 P0 未验证的范围不能被宣布兼容验收完成，风险接受需单独记录有权人员决定。

验收：按“服务端 SHA × 平台 × 旧营销版本／实测构建 × 场景 × 环境”记录实际结果；源码合同、测试构建、正式安装包和生产验收分别列示。

### P06：分批上线、观测与回退

在 P01–P05 相应发布条件满足且取得部署授权后，先核对待发布源、产物、环境、绑定、缓存、数据库台账及明确回退版本，再选择与该变更相符的切流方案。

- prod 可评估 Cloudflare 分批流量，但百分比和观察窗口需按实际流量与基线预先确定。混合版本下同一用户的连续请求可能跨版本，必须先通过 P03 的数据共存与幂等验证。
- 预先约定登录／Refresh、扫描成功与异常、额度账本、重复入库、权益同步和估值错误的观察指标；结合延迟、错误率、请求 ID 和实际业务样本判断，不以单次 health 200 证明兼容。
- 新 App 可增加可选版本／平台信息帮助分析；旧包缺失时标记未知，不能从不完整信息宣称已覆盖全部线上版本，也不能让缺 Header 的旧包被拒绝。
- 出现 P0 兼容失败或已约定停止条件时停止扩大流量，依据已验证方案回退或修复。Worker 代码回退不会自动还原 PostgreSQL／缓存中的数据；未验证数据兼容时不得盲目回滚。
- Linux dev 发布与 prod 发布分别记录；Git 合并、构建通过、部署成功和完整业务验收是不同结果。

验收：实际运行代码与批准产物一致，适用旧包业务烟测和指标通过，回退条件与未验证项清楚。记录写入 [v1.1.2 验证记录](VERIFICATION.md)，关联原版本证据，不覆盖历史结论。

## 5. 验证命令与证据要求

以下是实施阶段可使用的现有入口，不表示编写本文时已执行。前置为 Node 22、pnpm 11.9.0、Git/tar、Flutter 3.44.7、固定标签及锁定依赖；GitLab 独立 Flutter 工具链不在本次顺带调整。

```powershell
pnpm install --frozen-lockfile
flutter pub get --enforce-lockfile
pnpm --filter @kando/auth-core build
node --test scripts/check-app-compatibility.test.mjs
pnpm test:app-compatibility
```

按每批实际影响补充检查，先最小复现／合同，再扩展到受影响模块；新增测试文件的具体命令在实现时登记，不能把下面的概览当作所有模块已经验证：

| 变化范围 | 必须执行的验证 |
|---|---|
| 纯计划／文档 | 相对链接与引用检查、暂存前后 `git diff --check`；不要求全仓构建。 |
| 脚本、依赖或 CI | 相应 Node 脚本测试、`pnpm lint`、`pnpm type-check`、受影响构建／测试，以及隔离的失败阻断和成功正例。 |
| Workers 业务 | 受影响单元／集成测试及类型检查；涉及打包／入口时运行 prod/dev dry-run，明确两种运行时结果。 |
| Flutter／共享 Dart | 相关测试与 `flutter analyze`；跨包使用根 Melos 分析／测试；两平台边界分别说明。 |
| 数据或发布 | P03 的 PostgreSQL／共存验证、P04 的报告与产物一致性、P05/P06 的适用制品／环境证据。 |

新增发布检查脚本、完整 PostgreSQL 和 HTTP 集成命令在本计划中是待实现接口，不应在其不存在时标记为已执行。测试和业务控制使用确定性代码实现，不依赖模型判断是否放行。

源码归档、原始响应、日志和报告保存在既有忽略输出目录／受控 CI artifact；正式 docs 只保留业务契约、方案和必要验证摘要。避免上传真实账号 Token、插件 Key、Apple 私密凭据或用户图片。每次实现或审查返工后运行受影响验证；涉及 BUG 修复必须完成 Code Review 才能关闭。

## 6. 并行业务开发与后续接续

- 整改在 `codex/app-backward-compatibility` 独立进行；其他业务按已约定的方式从 main 建独立分支／worktree。不同聊天不共用正在修改的工作目录；本地端口和临时数据库分别配置，共享 dev 环境顺序验收。
- 新业务进入 main 后，在安全保存当前改动的前提下将该已交付基线合入整改分支，处理冲突并重跑受影响合同。代码能自动合并不证明契约兼容，特别关注 auth、scan、portfolio、entitlements、迁移和发布脚本。
- P01–P04 中独立稳定的增量可以分批评审交付，不必等完整真机验收后才整理代码；每批只声明已验证范围。未完成能力不能成为强制放行条件后再默认跳过。
- dev 若包含多条未完成工作，向 main 交付时明确选择已验收范围；main/dev 推送可能触发既有 CI／自动发布，仍按授权和发布边界执行。

后续切回本分支时，按以下顺序恢复工作：

1. 阅读本计划、当前 [兼容覆盖说明](../03-data-api/app-compatibility.md)、[验证记录](VERIFICATION.md)及根 AGENTS.md，确认此前阶段的真实提交和证据。
2. 检查实际分支、worktree、未提交改动、main 增量和固定基线；保留用户改动，不强制切换、清理或覆盖另一个任务。
3. 核对依赖与当前测试定义，先运行已有基线，再从最早未完成且前置条件齐全的阶段开始。基线失败先定位原因，不放宽断言。
4. 每批完成时提交必要代码／文档，记录已执行命令、退出状态、Code Review 及未执行原因到既有验证记录；本计划保持为设计与验收依据，不追加聊天交接日志。

## 7. 工作量、依赖与完成标准

初步工程工作量为 5–8 个工作日，其中代码与自动化约 3–5 个工作日；这是依据当前范围的估算，不是测试或发布完成承诺。若发现实际兼容 BUG、必须改变业务契约或无法取得制品，应重新评估对应增量。

| 工作包 | 预计工作量 | 前置条件 |
|---|---|---|
| P01/P02：基线、报告与核心业务合同 | 2–3 天 | 工具链／固定标签／依赖可用；旧请求和既有业务规则明确。 |
| P03/P04：数据库、共存与发布入口 | 1–2 天 | 隔离 PostgreSQL 18 可用；发布报告来源与实际入口确认。 |
| P05：旧包、真机和外部服务 | 1–2 天 | 可获取旧制品、设备、测试账号、Apple Sandbox 及相关授权。 |
| P06：分批上线、观察和修正预留 | 0.5–1 天 | 适用 P0 放行条件满足；部署／生产测试授权和观察窗口明确。 |

包、设备、账号或授权的等待时间不计入上述工作量。首次可评审的小批次预计 0.5–1 天；其通过仅证明该批交付范围。

整改完成需同时满足以下条件：

- 受支持集合和适用 C01–C13 范围明确，保留固定旧源码与已知构建差异；正式包证据单列。
- 必需旧端业务合同和跨版本数据断言通过，已证明相关失败反例能被捕获；无静默跳过、伪造空成功或未经依据的不适用。
- 完整目标 PostgreSQL schema、缓存和已选回退版本兼容性有实际证据。
- 各发布入口对错误 SHA／报告／产物和未完成检查确实拒绝发布，可信正例可完成流程；没有恢复已取消的推送／合并强制规则。
- 适用旧包／平台／外部服务和授权环境验收有记录；缺失项仍保持未验证，不据此宣布整个受支持范围完成。
- 相关代码与行为文档一致，BUG 修复审查完成，线上变更按独立授权执行，正式记录可追溯。
