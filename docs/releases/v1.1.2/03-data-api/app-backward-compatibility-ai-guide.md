# App 向后兼容开发规则（v1.1.2，AI 执行版）

更新日期：2026-10-14（Asia/Shanghai）。适用于后续涉及 App API、共享业务数据或客户端协议的开发与修改。产品意图见 [阅读版](../05-delivery/app-backward-compatibility-plan.md)，操作与安全边界见[根 AGENTS.md](../../../../AGENTS.md)。

本版本的 App 兼容资料只维护[阅读版](../05-delivery/app-backward-compatibility-plan.md)与本文两份；测试入口、覆盖缺口和必要证据摘要合并在本文，不另建兼容说明或验证文档。本文把已确认的兼容原则转成开发约束，不授权自行开展全部整改、创建 V2、改动远端规则或发布。开发时只执行用户当前明确的需求；文档规则不等于实现或验收结果。

**执行范围：** 规则阅读、确认与落实任务只维护规则和文档入口，不自动修改业务代码、扩展测试或调整 CI。开发与验证范围须来自具体功能需求、已证实且属于当前任务的兼容 BUG，或用户明确的补测要求；其余情况下保持现有实现。

## 1. 目标与基线

> 以现有 `/api/v1` 对外约定为基础；新功能优先复用 V1，新增请求字段可选且省略时保持旧行为，新增响应字段须能被旧 App 忽略；无法兼容扩展时只为受影响功能新增 `/api/v2`，同时保留 V1。

| 项目 | 依据与执行要求 |
|---|---|
| 服务端接口基线 | 当前 [Hono 组合入口](../../../../apps/workers-api/src/app.ts)主要挂载 `/api/v1`；以本次需求修改前、已对 App 提供的接口约定为基础，读取旧调用方核对，不能把改后的实现当成旧标准。 |
| 支持范围 | 继承 [App 1.0.4+ 契约](../../v1.1.1/03-data-api/app-compatibility-contract.md)；未经明确产品决定，不提高最低支持版本，不恢复范围外的旧 pHash 协议。 |
| 固定旧客户端 | [基线登记](../../../../scripts/app-compatibility-baselines.json)固定 1.0.4+161、1.0.5+163 的 SHA；只作为源码协议证据，不能改旧 SHA／源码来让检查通过。新增支持版本时追加相应基线。 |
| 当前源码证据 | 本文第 6 节说明已有测试与覆盖缺口，并保留历史证据摘要；不能推断所有正式包、真机或生产环境已通过。 |
| API 版本 | App 营销版本、构建号、API 主版本分别管理。既有卡牌 `response_version=2` 已被旧客户端使用，它不是 `/api/v2`，也不能当作仅新版发送的识别开关。 |

每项开发在修改前记下当前分支／提交、受影响接口、旧请求／响应和业务预期。可在当前需求或交付说明中记录，不要求新建一套登记平台。发现代码与旧契约冲突时，暴露冲突并定位；禁止静默将不兼容现状认定为新的基线。

## 2. 必须遵守的规则

| ID | 规则 | AI 执行要求 |
|---|---|---|
| R01 | 保留旧接口约定 | 保留旧路径、方法、成功与错误包络、字段名称／类型／可空性、分页与默认行为。不重定向或替换旧调用入口来强迫旧 App 使用新协议。 |
| R02 | 新请求字段可选 | 在校验和业务处理中都可省略；省略时保持原有行为。新增 Header 同样不能成为旧请求的必需项。不能只在 DTO 上写 optional，而在后续逻辑中强制使用。 |
| R03 | 新响应字段可忽略 | 保留原字段及含义，核对固定旧客户端如何解析。未知字段和未知枚举不是同一回事；不得向旧版已有状态字段直接输出它无法处理的新值。 |
| R04 | 原有业务结果正确 | 价格 `0` 与缺价 `null`、字符串 `card_ref`、币种／历史范围／排序、错误语义保持既定定义；服务失败不能变成成功空数据。 |
| R05 | 共享数据不被旧操作破坏 | 在旧版支持的业务范围内，新版写入后旧版能读取并执行原有操作。旧请求缺少新增属性时保留已存值；显式清空按具体接口契约处理，不混同省略字段和 `null`。 |
| R06 | V2 局部新增、V1 保留 | 无法兼容扩展的请求／返回／业务语义放到受影响的 `/api/v2` 接口。V1 仍按旧约定提供服务，其余兼容功能仍可使用 V1。 |
| R07 | 权限与权益继续可信 | 新旧接口维持服务端鉴权、owner 隔离、会话、幂等、额度和购买验证。不能用客户端版本或自报 Premium／UID 作为授权依据。 |
| R08 | 只改当前影响范围 | 不整套复制 V1、不顺手重构、不批量新建 V2、不恢复 D1、不自行增加发布门禁。开发和必要文档修改完成后再测试，只验证受影响功能及共享调用方。 |

## 3. V1／V2 决策顺序

按下面顺序决定，不根据“新功能”三个字直接升级 API：

1. **已有接口能直接满足需求：** 复用现有 V1，保持旧约定。
2. **增加可选字段即可满足：** 扩展 V1，明确省略时的旧行为及响应新增字段的旧端解析方式。
3. **需求是独立新增功能，没有改变旧接口：** 可以在 V1 下新增独立路由；若需求已经明确指定 V2，则按该设计执行。
4. **需求必须改变旧约定：** 写清具体不兼容点，为受影响功能设计局部 V2，保留 V1。仅当该需求和接口设计已获授权时实施；有会改变实现范围的歧义时，先向用户澄清。

| 变化 | 默认处理 |
|---|---|
| 可选筛选参数，缺省结果不变 | V1 兼容扩展。 |
| 独立响应字段，旧解析器能忽略 | V1 兼容扩展。 |
| 仅内部查询或性能优化，对外行为不变 | 保持 V1。 |
| 旧请求必须多传参数才成功 | 不修改 V1；满足已确认新需求的 V2 接受新参数。 |
| 删除／改名旧字段、改变字段类型／返回层级 | 不修改 V1；新结构使用 V2。 |
| 旧状态字段增加旧 App 无法处理的枚举 | 保留 V1 可理解的表达；新状态按已确认的 V2 设计处理，不能无依据映射成旧状态。 |

## 5. 实施顺序与边界

1. **读取与定位。** 检查分支／工作区，保留用户改动；阅读契约、代码和已有证据。此阶段不启动测试。BUG 先用已有日志、请求样本、堆栈或代码路径确认实际行为和根因，不凭猜测改代码。
2. **确定最小方案。** 按 R01–R08 说明 V1／V2 决策与影响范围。真实 BUG 的定位证据、兼容规则冲突和未确定事项必须暴露。
3. **完成开发及文档修改。** 只实现当前需求，按风险补充表达业务意图的相关测试，但完成前不运行；同步更新实际行为和必要说明。
4. **完成后验证。** 开发代码、测试代码和必要文档的修改都完成后，运行最小相关检查，再按已识别影响扩展。发现失败并返工时，返工完成后重新验证受影响范围。
5. **审查并交付。** 自查旧约定是否保持。BUG 按根 AGENTS.md 完成 Code Review；审查返工后重新验证和审查。分别报告通过、失败、未运行及原因，不把文档完成写成业务或生产验收完成。

测试时序以用户“任务完成后再测试”的要求为准。BUG 修改前的失败证据优先使用已获得的日志、请求、堆栈等；没有修复前运行测试时要记录原因。开发完成后，可在隔离环境用同一回归用例验证旧逻辑失败、修复逻辑通过，禁止影响用户工作区或远端业务数据，也不能把这一反证写成修复前已经实测。

新增 V2 时只注册必要路由，复用现有业务能力。检查新路径是否正确接入鉴权、请求 ID、CORS、幂等与错误处理；这些能力在 V1 上存在，不代表会自动覆盖 V2。不要为了版本化复制整个业务层。

共享数据处理区分“字段未提交”“显式 null”“具体值”。具体清空语义由该接口契约确定，不能用统一默认值覆盖。新功能独有数据如何向旧端呈现，需结合真实旧解析器明确策略；不能隐藏或破坏旧资产来掩盖失败。

schema、KV/R2/Hyperdrive binding 变更先说明兼容、回退和环境影响；新增 migration 只进入 PostgreSQL 目录。只有实际涉及数据／缓存／运行入口时才补相应验证。旧服务端回退、数据库恢复和发布门禁是独立工程范围，不能自动加入每个兼容需求。

分类、筛选和简单语义判断优先使用 TypeSafe/Jev，说明实际使用步骤；复杂兼容分析由 Codex 结合代码证据完成。Git 操作、数据转换、请求路由和测试执行使用确定性代码。Jev 分类不是代码正确、兼容通过或授权的证明；不发送凭据或无关私有业务内容。

### 6.1 已有测试怎么运行

根目录入口是 `pnpm test:app-compatibility`。前置为 Node 22+、pnpm 11.9.0、Git／tar、Flutter 及已解析的 Node／Dart workspace 依赖。已有 GitHub 兼容流水线使用 Flutter 3.44.7；不要顺带统一其他流水线工具链。

在依赖缺失的本地环境，按既有锁文件准备依赖；已有依赖时无需重复安装。开发与必要文档修改完成后，按影响选择检查：

```bash
pnpm install --frozen-lockfile
flutter pub get --enforce-lockfile
pnpm --filter @kando/auth-core build
pnpm test:app-compatibility
```

依赖安装和 auth-core build 是运行前置；这不是每个需求都必须执行的整套测试清单。只有修改基线登记／编排脚本时，才额外执行 `node --test scripts/check-app-compatibility.test.mjs`。类型、静态检查和受影响模块命令遵循[根 AGENTS.md](../../../../AGENTS.md)。

编排脚本先在本地内存 PostgreSQL 中调用当前 Hono API，产出真实测试响应；再导出固定旧源码，核对旧客户端发出的请求和解析／业务结果。它使用当前解析依赖，证据类型为 `git-source-contracts-only`，不会联网调用 dev／prod 业务 API，也不运行远程迁移。不要用当前客户端替换固定旧源码，或修改冻结基线来让结果通过。

命令当前没有单场景筛选参数，适用时运行现有集合，不为了缩小范围删减既有测试。测试工具、依赖或旧基线缺失时明确记录未运行原因；未覆盖的受影响场景补相应测试，不能只测最新客户端后声称旧版通过。

源码快照、原始响应和 `report.json` 输出到忽略目录 `.dart_tool/app-compatibility/run-*/`，报告记录服务端 SHA、dirty 状态与旧基线。文档仅保存必要结果摘要，日志和原始材料留在忽略目录／受控 CI artifact；历史机器的输出目录不代表本机现在拥有相同材料。

### 2026-10-12 Home 文件夹切换（历史本地证据）

此项是原验证文档中的独立 BUG，保留其追溯信息，不作为 App 兼容通过的证据，也不改变上面的开发规则。以下均为历史记录，本次未重跑。

- 用户 iOS 录屏：Home 显示 Main 和旧金额，页面出现两个 `No content available`；从共用弹窗选择其他文件夹后，Collection 已切换，返回 Home 仍显示 Main。录屏没有网络日志，不能据此确定 Home 数据请求失败的服务端原因。
- 根因：Home 的全局 `selectedPortfolioFolderProvider` 监听在 `isUnavailable` 时直接跳过；即使 Collection 已更新共享选择，Home 仍保留失败前的文件夹 ID。修复前使用“首次加载成功、随后 Home 刷新持续失败、通过共用弹窗切换文件夹”的 widget 测试复现，退出 1，断言 Home 为 `sealed` 时实际仍为 `main`。
- 最小修复：共享选择变更时，先用 Home 已缓存的目标文件夹更新 ID 和图表周期，再刷新 Home；刷新失败仍保留正确的文件夹上下文和原有失败提示。未修改服务端接口、偏好持久化语义、Collection 切换逻辑、Schema 或部署配置。v1.0.0 已有 Home/Collection 同步切换契约，本轮不改冻结文档。
- 影响与验证：对 Home/Collection 共用选择、失败后重试、图表周期和偏好写入回退作代码审查；目标测试修复前失败、修复后通过。`flutter test --no-pub test/home_controller_test.dart test/collection_controller_test.dart test/widget/home_page_test.dart test/widget/collection_page_test.dart` 退出 0，共 170 项；`flutter analyze --no-pub lib/features/home/home_controller.dart test/widget/home_page_test.dart` 退出 0；`git diff --check` 退出 0。Code Review 未发现当前变更的阻断项。
